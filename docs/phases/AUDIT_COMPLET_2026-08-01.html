Audit complet du projet — MedAnki DZ

Branche arena/019fbd6a-medlm · commit 2628896 · 2026-08-01 · périmètre : backend NestJS, mobile Flutter, CMS Next.js, outillage Python, contenu, infra K8s, docs

1. Avis général (ce que je pense du projet)

C'est, sans exagération, le noyau le plus rigoureux d'un projet étudiant/DZ que j'aie audité ici : le moteur FSRS est vérifié à 855 valeurs + 275 mesures de séquences contre l'implémentation officielle ts-fsrs, le schéma SQL et les tables Drift sont maintenus en parité par des gardes bloquants, la politique de contenu est testée (722 vérifications), l'audit sécurité statique tourne à chaque push (0 contrôleur non gardé, 0 @Body non validé, 0 secret), l'i18n du backend est en parité FR/AR/EN, et la conformité légale algérienne (loi 18-07, 09-04) est traitée comme du code (PRIVACY, SECURITY, pentest_prep). Ce niveau de discipline est rare.

Mais le code « 100 % terminé » n'existe pas encore : le projet est au stade de bibliothèques à ~95 % complètes + produit non assemblé. L'application mobile n'a ni main.dart, ni écrans d'authentification/accueil/examen, ni dossiers platform (android/ios), ni fichier Drift généré : elle ne compile pas — c'est la dernière ligne droite, la plus visible pour l'utilisateur final. Il n'y a aucune CI/CD (les « workflows » mentionnés dans les commentaires n'existent pas), aucun Dockerfile alors que les manifests K8s référencent des images, et le dépôt contient encore les restes du prototype Google AI Studio (Kotlin app/, wheel nothing, README scaffold, .env.example Gemini). Enfin, l'audit a trouvé un vrai bug de routage : le gateway GraphQL déclaré v2/graphql sous un préfixe global v1 — l'endpoint réel est /v1/v2/graphql, le client mobile appelle /v2/graphql → 404. Ce bug a été corrigé le jour même, et sa correction a révélé une cascade de 4 bugs de production supplémentaires (l'app ne bootait pas hors tests unitaires ; toutes les erreurs de validation retournaient 500 au lieu de 400) — voir §5.1.

Estimation d'effort vers « 100 % produit » : 2 à 4 semaines de travail focalisé (mobile shell + CI/build + nettoyage), puis la phase récurrente opérationnelle (device, stores, pen test) qui elle, n'est pas du code.

5. P0 — Bloqueurs À corriger avant tout

P0-1 · Bug de routage : le gateway GraphQL répond sur /v1/v2/graphql, le mobile appelle /v2/graphql → 404  ✓ CORRIGÉ LE 2026-08-01

Preuve : backend/src/main.ts:16 → app.setGlobalPrefix('v1') (sans exclusion) · backend/src/gateway/gateway.controller.ts:22 → @Controller('v2/graphql') · mobile/lib/data/network/api_client.dart → _dio.post('/v2/graphql'). Les tests unitaires du gateway testent le service, pas le routage — d'où l'invisibilité du bug.

✓ Corrigé : v2 exclu du préfixe global (app.setGlobalPrefix('v1', { exclude: [{ path: 'v2/graphql', method: RequestMethod.ALL }] })) dans la nouvelle fonction partagée configureApp() (src/configure-app.ts), verrouillé par test/integration/routing.test.ts (3 tests supertest : /v2/graphql ≠ 404, /v1/v2/graphql = 404, préfixe v1 intact). La correction a exigé de réparer toute la chaîne de tests d'intégration — ce qui a mis au jour 4 bugs de production supplémentaires (voir encart §5.1 ci-dessous), dont un qui empêchait l'application de booter hors tests unitaires. Effort réel : ½ journée, comme estimé.

P0-2 · Le mobile ne peut pas être compilé ni lancé : pas de main.dart, pas de dossiers platform, Drift non généré

Preuve : find mobile -name "main*.dart" → rien · ls mobile/{android,ios} → inexistants · app_database.dart:20 → part 'app_database.g.dart' alors qu'aucun .g.dart n'existe dans le repo (ni gitignoré — simplement jamais généré), pubspec.lock épingle drift 2.18.0. Les 71 fichiers de lib/ (domain/data/core/ui avec 4 Écrans IA + 2 gamification + 1 étude importés nulle part) forment une bibliothèque, pas une app.

Fix : (a) flutter create --platforms=android,ios . dans mobile/, (b) dart run build_runner build (committer ou générer en CI — trancher, mais verifier en CI que le fichier est à jour), (c) écrire main.dart + routeur (go_router) + AppContainer wiring + PackageInfo/save, (d) créer les Écrans manquants (P1-3). Effort : 1–2 semaines. C'est LE chantier « 100 % ».

P0-3 · CI/CD absente : .github/workflows/ n'existe pas (référencé par le code et les docs)

Preuve : ls .github/workflows → vide · pourtant database.module.ts cite « cf. workflow backend-ci.yml » et le plan liste une Phase 12 CI/CD. Conséquence : rien ne rejoue tsc/vitest/eslint/typecheck CMS/verify_all à chaque PR ; dart test n'est exécuté nulle part ; les tests d'intégration (vraie Postgres) ne tournent jamais.

Fix : créer les workflows depuis un compte disposant de la permission workflows (l'app GitHub de session ne l'a pas) : backend-ci.yml (node 22, npm ci, tsc, vitest, eslint + service Postgres pour test:integration), mobile-ci.yml (flutter test + analyze + build_runner --verify), cms-ci.yml, guards.yml (verify_all + phase13 + audits). Effort : 1 jour. Priorité immédiate après P0-1.

P0-4 · Aucune image constructible : pas de Dockerfile backend ni CMS alors que K8s référence medanki/backend:latest et medanki/cms:latest

Preuve : find . -name "Dockerfile*" → 0 résultat · deploy/k8s/base/backend-deployment.yaml & cms-deployment.yaml attendent ces images. De plus, backend/.env.example dit « docker compose up -d postgres » mais aucun docker-compose.yml n'existe dans le dépôt.

Fix : backend/Dockerfile (node:22-alpine, multi-stage build nest, user non-root, healthcheck /v1/healthz), cms/Dockerfile (next build → standalone), docker-compose.yml dev (postgres + redis + backend + cms) + vérification en CI (docker build). Effort : 1 jour.

P1-3 · Notifications : chaîne incomplète des deux côtés

Mobile : aucun package FCM/APNs dans pubspec.yaml, aucune remontée de device token vers le backend, aucun écran de permission. Backend : FCM_PROVIDER lit FIREBASE_ACCESS_TOKEN statique depuis l'env — or les tokens OAuth2 expirent ~1 h : en production réelle l'envoi s'arrêtera (le commentaire annonce google-auth-library jamais branchée). apns/ est un dossier quasi vide.

Fix : backend — utiliser google-auth-library (JWT signé par compte de service, cache + rotation) avec repli test ; mobile — ajouter firebase_messaging (+ firebase_core), POST d'enregistrement du token au backend, deep-link vers l'étude ; APNs plus tard (Android first). Effort : 3–4 jours.

P1-4 · i18n mobile : les chaînes UI sont en dur en français

Le backend est trilingue vérifié (i18n_parity 14 tests), mais côté mobile : leaderboard_screen.dart le dit lui-même (« les chaînes sont en dur »), il n'y a pas d'AppLocalizations/intl déclaré, et les nouveaux écrans (étude, IA, ML) sont FR-only. Pour une app DZ, l'arabe est attendu.

Fix : adopter flutter_localizations + intl, extraire les ~40 chaînes existantes dans app_fr.arb/app_ar.arb/app_en.arb une seule fois (avant que les Écrans P1-2 ne se multiplient — sinon le coût double), garder le serveur comme source des textes IA (déjà le cas). Effort : 2 jours.
